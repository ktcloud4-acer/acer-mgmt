Acer 프로젝트 백업 구조

각 팀 AIO 클러스터와 mgmt 서버의 데이터를 목적별로 나누어 백업하고, mgmt MinIO와 AWS S3에 단계적으로 보관하는 구조입니다.

GitOps 백업 Schedule과 CronJob을 Argo CD로 배포
MinIO 팀별 prefix로 백업 결과 중앙 보관
도구 분리 K8s 리소스, DB, 파일, etcd를 각각 다른 방식으로 백업
Offsite MinIO 백업 bucket을 AWS S3로 추가 복제

1. 결과물이 도출된 과정

처음에는 “namespace만 백업하면 되는가?”에서 출발했고, 실제 데이터의 성격을 나눈 뒤 Kubernetes 리소스, DB 데이터, 파일, 클러스터 상태를 각각 맞는 도구로 백업하도록 구성했습니다.

1

백업 대상 분류

GitOps 리소스, Secret, PostgreSQL 데이터, Storage 파일, mgmt 설정, etcd 상태를 분리했습니다.

2

도구 선택

Velero, pg_dump, tar, restic, etcdctl snapshot을 데이터 성격에 맞게 배치했습니다.

3

자동화 구현

Argo CD, Kubernetes CronJob, systemd timer, Docker Compose 반복 실행으로 정기 백업을 구성했습니다.

4

중앙 보관과 외부 복제

mgmt MinIO에 bucket별로 모으고, MinIO bucket을 AWS S3에 복제해 외부 저장소를 추가했습니다.

2. 전체 백업 아키텍처

백업은 mgmt가 모든 것을 대신 실행하는 방식이 아닙니다. 각 AIO 클러스터는 자기 클러스터의 Kubernetes 리소스와 etcd snapshot을 직접 만들고, 결과를 mgmt MinIO endpoint로 업로드합니다. mgmt 서버 데이터는 mgmt 내부의 systemd/restic 작업이 백업합니다.

각 AIO 클러스터: ljw, ggg, khb, nmg, oje
Velero Schedule web-service, tailscale namespace 백업
etcd CronJob control-plane에서 snapshot.db 생성
mgmt 서버 내부 백업
DB dump Supabase PostgreSQL, Storage, 설정 백업
restic /home/mgmt-data 파일 기반 서비스 볼륨 백업

3. 활용 기술과 역할

하나의 도구로 모든 것을 백업하지 않고, 데이터의 성격에 맞는 도구를 조합했습니다.

Velero

Kubernetes 리소스 백업

namespace, Deployment, Service, Secret 등 Kubernetes API 리소스를 MinIO velero bucket에 저장합니다.

pg_dump

PostgreSQL 논리 백업

회원 데이터처럼 DB 안에 들어있는 실제 서비스 데이터는 PostgreSQL dump 파일로 백업합니다.

restic

mgmt 파일 볼륨 백업

Harbor, GitLab, Grafana 등 /home/mgmt-data 아래 파일 기반 데이터를 암호화 snapshot으로 백업합니다.

etcdctl

클러스터 제어면 상태 백업

각 AIO control-plane의 etcd snapshot을 생성해 MinIO etcd bucket에 저장합니다.

Argo CD

GitOps 배포

팀별 backup overlay를 각 클러스터에 배포해 Velero Schedule과 etcd CronJob을 관리합니다.

AWS S3

외부 저장소 복제

mgmt MinIO 자체 장애를 대비해 db-backup, etcd, velero, restic bucket을 외부로 복제합니다.

4. 백업 스케줄

백업 시간은 오후 시간대로 분리했습니다. DB와 파일 백업, etcd snapshot, namespace 백업, 외부 복제가 서로 겹치지 않게 배치했습니다.

백업 항목 시간 실행 위치 저장 위치
mgmt DB / Storage / Config / k3d datastore 매일 15:30 KST mgmt systemd timer MinIO db-backup, 로컬 /home/mgmt-data/backups
AIO etcd snapshot 매일 15:40 KST 각 클러스터 Kubernetes CronJob MinIO etcd/<team>/daily
web-service / tailscale namespace 매일 16:00 KST 각 클러스터 Velero Schedule MinIO velero/<team>
mgmt host volume 매일 16:20 KST mgmt restic container MinIO restic
MinIO bucket offsite mirror 매일 16:30 KST mgmt systemd timer AWS S3 bucket

5. MinIO bucket별 백업 결과

백업 결과는 목적별 bucket으로 나뉩니다. 발표에서는 “무엇을 어디에 저장하는지”만 잡아도 전체 구조가 이해됩니다.

bucket: velero

Kubernetes namespace 리소스 백업.

velero/ljw, velero/ggg처럼 팀별 prefix로 분리합니다.

bucket: etcd

AIO control-plane etcd snapshot.

etcd/ljw/daily/<timestamp>/snapshot.db 구조로 저장합니다.

bucket: db-backup

Supabase PostgreSQL, Storage, mgmt 설정, k3d datastore 백업.

systemd timer가 매일 15:30 KST에 생성합니다.

bucket: restic

Harbor, GitLab 등 mgmt 파일 볼륨 snapshot repository.

/home/mgmt-data/minio는 제외하고 백업합니다.

6. 구현 결과 화면으로 보여줄 포인트

실제 발표 자료에는 아래 네 가지 화면을 캡처하면 충분합니다. 너무 많은 명령어보다 결과 화면 중심으로 보여주는 것이 이해하기 쉽습니다.

Argo CD

팀별 velero-schedule-* Application이 Healthy/Synced인지 보여줍니다.

velero-schedule-ljw velero-schedule-ggg velero-schedule-khb velero-schedule-nmg velero-schedule-oje

MinIO bucket

bucket별로 백업 산출물이 분리되어 저장되는 화면을 보여줍니다.

db-backup/ etcd/ restic/ velero/

팀별 prefix

여러 팀 백업이 같은 bucket 안에서도 prefix로 분리되는 것을 보여줍니다.

velero/ ggg/ khb/ ljw/ nmg/ oje/

AWS S3 offsite

MinIO bucket이 외부 S3에도 복제되어 mgmt 서버 장애까지 대비하는 구조를 보여줍니다.

acer-minio-backup-.../ db-backup/ etcd/ restic/ velero/
발표 핵심 문장: Kubernetes 리소스는 Velero, DB 데이터는 pg_dump, 파일 볼륨은 restic, 클러스터 제어면 상태는 etcd snapshot으로 나누어 백업했습니다.
