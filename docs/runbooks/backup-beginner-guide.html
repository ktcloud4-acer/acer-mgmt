1. 백업을 왜 해야 하나

백업은 장애가 생겼을 때 이전 상태로 돌아가기 위한 안전장치다. 운영에서는 실수 삭제, 잘못된 배포, DB 손상, 서버 장애, 클러스터 장애가 언제든 발생할 수 있다.

좋은 백업의 기준

파일이 저장되어 있는 것만으로는 부족하다. 실제로 복구할 수 있어야 좋은 백업이다. 그래서 백업 생성과 복구 테스트는 항상 같이 봐야 한다.

우리 프로젝트는 데이터 종류가 하나가 아니다. Kubernetes 리소스, PostgreSQL DB, 업로드 파일, mgmt 서버 볼륨, 클러스터 control-plane 상태가 서로 다르다. 그래서 한 도구로 전부 백업하지 않고, 데이터 성격에 맞는 도구를 나눠서 사용한다.

2. 현재 구조 한 줄 요약

가장 중요한 문장

현재 web-service는 GitOps 리소스 중심이라 namespace 백업이 맞고, DB/파일/클러스터 상태는 각각 pg_dump, tar, restic, etcd snapshot으로 따로 백업하고 있다.

web-service Velero namespace

Deployment, Service, ConfigMap, Secret 같은 Kubernetes 리소스 백업

mgmt 데이터 pg_dump tar restic

Supabase DB, Storage 파일, mgmt 설정, host volume 백업

AIO 클러스터 상태 etcdctl snapshot

Kubernetes control-plane 전체 상태를 etcd snapshot으로 백업

3. 왜 web-service는 namespace 백업인가

web-service에는 manifest 파일이 많다. 예를 들면 다음과 같다.

fastapi-deployment.yaml
fastapi-service.yaml
nginx-configmap.yaml
nginx-deployment.yaml
nginx-service.yaml
namespace.yaml
secret.example.yaml
servicemonitor.example.yaml

이 파일들은 대부분 Kubernetes 리소스 정의다. 즉 "사용자 데이터 파일"이라기보다 "클러스터에 어떤 앱을 어떻게 띄울지"를 설명하는 설정이다.

리소스 의미 Velero namespace 백업 대상인가
Deployment Pod를 몇 개 띄울지, 어떤 이미지로 실행할지 정의 예
Service Pod로 트래픽을 보내는 내부 네트워크 엔드포인트 예
ConfigMap Nginx 설정 같은 일반 설정값 예
Secret 민감 설정값. 실제 클러스터에 생성된 Secret 기준 예
PV/PVC 데이터 디스크에 저장되는 실제 파일 데이터 현재 설정에서는 아니오
중요한 구분

Git에 YAML 파일이 많다는 것과, 앱이 직접 저장하는 데이터가 많다는 것은 다르다. 현재 web-service는 GitOps로 다시 배포 가능한 Kubernetes 리소스 중심이다.

그래서 현재 Velero는 web-service namespace 안의 리소스를 백업한다. 반면 DB나 업로드 파일처럼 실제 상태 데이터는 mgmt 쪽에서 별도 백업한다.

4. 백업 도구별 역할

도구 쉽게 말하면 우리 프로젝트에서 백업하는 것 저장 위치
Velero Kubernetes 리소스 백업 도구 각 팀 AIO의 web-service namespace MinIO velero bucket
etcdctl snapshot Kubernetes control-plane 상태 저장소 백업 ggg, khb, ljw, nmg, oje AIO의 etcd snapshot MinIO etcd bucket
pg_dump PostgreSQL DB를 복구 가능한 파일로 추출 Supabase PostgreSQL 데이터 MinIO db-backup bucket
tar 디렉터리를 압축 파일로 묶음 Supabase Storage 파일, mgmt 설정 MinIO db-backup bucket
restic 서버 디렉터리 스냅샷 백업 /home/mgmt-data 주요 볼륨 MinIO restic bucket
MinIO S3 호환 백업 저장소 위 백업 파일들이 모이는 저장소 mgmt 서버

5. MinIO bucket별 의미

db-backup

mgmt 서버에서 직접 만든 백업 산출물이 들어간다. DB, 파일, 설정처럼 사람이 보고 이해하기 쉬운 백업 파일이 저장된다.

db-backup/
  supabase-postgres/daily/<timestamp>/
    postgres.dump
    globals.sql
    SHA256SUMS

  supabase-storage/daily/<timestamp>/
    supabase-storage.tar.gz
    SHA256SUMS

  mgmt-config/daily/<timestamp>/
    mgmt-config.tar.gz
    SHA256SUMS

  k3d-mgmt-datastore/daily/<timestamp>/
    k3s-sqlite-datastore.tar.gz
    SHA256SUMS
항목 무엇을 백업하나 복구할 때 쓰는 방법
supabase-postgres 사용자 테이블, 인증 데이터, schema, function 등 PostgreSQL 데이터 pg_restore, psql
supabase-storage 사용자가 업로드한 이미지, 첨부파일, 문서 파일 tar -xzf로 Storage 디렉터리에 복원
mgmt-config .env, compose, secrets, k3d 설정, Argo CD repo 새 mgmt 서버 bootstrap 시 압축 해제
k3d-mgmt-datastore mgmt k3d/K3s SQLite datastore k3d/K3s 중지 후 datastore 복원

etcd

AIO 클러스터의 etcd snapshot이 팀별 prefix로 저장된다.

etcd/
  ggg/daily/<timestamp>/snapshot.db
  khb/daily/<timestamp>/snapshot.db
  ljw/daily/<timestamp>/snapshot.db
  nmg/daily/<timestamp>/snapshot.db
  oje/daily/<timestamp>/snapshot.db

etcd snapshot은 namespace 하나를 복구하는 용도가 아니라, control-plane 장애 시 클러스터 상태를 되살리기 위한 백업이다.

velero

Velero가 만든 Kubernetes 백업 metadata가 들어간다. 팀별 prefix로 분리되어 있다.

velero/
  ggg/backups/
  khb/backups/
  ljw/backups/
  nmg/backups/
  oje/backups/

restic

restic repository다. 사람이 직접 파일을 열어보는 구조가 아니라 restic CLI로 조회하고 복구한다.

restic/
  config
  data/
  index/
  keys/
  snapshots/
주의

restic은 /home/mgmt-data를 백업하지만 /home/mgmt-data/minio는 제외한다. 따라서 MinIO 자체가 날아가는 상황까지 대비하려면 MinIO bucket을 AWS S3 같은 외부 저장소에 추가 복제해야 한다.

6. 백업 스케줄

백업 시간 왜 이 시간인가
mgmt DB/Storage/Config/k3d 매일 15:30 KST 오후 백업 흐름의 시작점으로 DB dump와 파일 백업을 먼저 생성
AIO etcd snapshot 매일 15:40 KST mgmt 백업과 겹치지 않도록 10분 뒤에 클러스터 상태 snapshot 생성
Velero web-service namespace 매일 16:00 KST namespace 리소스 백업. etcd snapshot 이후 실행
restic host volume 매일 16:20 KST 컨테이너 내부에서 다음 16:20 KST까지 대기 후 실행
restic 시간 주의

restic은 매일 16:20 KST에 맞춰 실행되도록 컨테이너 내부 대기 로직을 사용한다. 컨테이너 재시작 후에도 다음 16:20 KST 실행 시각을 다시 계산한다.

7. bucket별 복구 테스트 방법

1. 백업 선택

MinIO에서 timestamp를 보고 복구할 백업 시점을 정한다.

2. 임시 위치 복구

운영 위치가 아니라 테스트 디렉터리나 테스트 DB에 먼저 복구한다.

3. 무결성 확인

SHA256SUMS, DB 접속, 파일 목록 등을 확인한다.

4. 운영 복구

절차가 검증된 뒤 운영 복구를 진행한다.

db-backup: Supabase PostgreSQL

mc cp --recursive local/db-backup/supabase-postgres/daily/<timestamp>/ ./restore-postgres/

# 테스트 PostgreSQL에 복구
psql -U postgres -f restore-postgres/globals.sql
pg_restore -U postgres -d postgres --clean --if-exists restore-postgres/postgres.dump

db-backup: Supabase Storage

mc cp local/db-backup/supabase-storage/daily/<timestamp>/supabase-storage.tar.gz .
mkdir -p /tmp/storage-restore-test
tar -xzf supabase-storage.tar.gz -C /tmp/storage-restore-test
find /tmp/storage-restore-test -type f | head

db-backup: mgmt-config

mc cp local/db-backup/mgmt-config/daily/<timestamp>/mgmt-config.tar.gz .
mkdir -p /tmp/mgmt-config-test
tar -xzf mgmt-config.tar.gz -C /tmp/mgmt-config-test
find /tmp/mgmt-config-test -maxdepth 3 -type f | sort

etcd

mc cp --recursive local/etcd/ljw/daily/<timestamp>/ ./restore-etcd/
cd ./restore-etcd
sha256sum -c SHA256SUMS
etcdctl snapshot status snapshot.db --write-out=table
주의

etcd restore는 운영 클러스터에 가볍게 실행하는 테스트가 아니다. control-plane 복구 절차이므로 격리된 테스트 환경에서 검증해야 한다.

velero

velero backup get
velero backup describe <backup-name> --details

# 합의된 테스트 환경에서만 namespace 삭제 복구 테스트
kubectl delete ns web-service
velero restore create web-service-restore-test --from-backup <backup-name>
velero restore describe web-service-restore-test --details
kubectl get all -n web-service

restic

docker exec restic restic snapshots
docker exec restic restic ls latest /source

# 운영 위치가 아니라 임시 위치에 먼저 복구
docker run --rm --network mgmt-proxy \
  -e RESTIC_REPOSITORY=s3:http://minio:9000/restic \
  -e RESTIC_PASSWORD="$RESTIC_PASSWORD" \
  -e AWS_ACCESS_KEY_ID="$RESTIC_ACCESS_KEY" \
  -e AWS_SECRET_ACCESS_KEY="$RESTIC_SECRET_KEY" \
  -v /home/mgmt-data-restore-test:/restore \
  restic/restic:0.19.0 \
  restore latest --target /restore --include /source/grafana

8. 팀원이 꼭 기억할 것

  1. web-service는 GitOps 리소스 중심이라 현재는 Velero namespace 백업이 맞다.
  2. DB는 Velero가 아니라 pg_dump로 백업하고 복구한다.
  3. 업로드 파일은 Supabase Storage tar 백업으로 복구한다.
  4. 클러스터 전체 control-plane 상태는 etcd snapshot으로 보호한다.
  5. mgmt 서버 볼륨은 restic이 백업하지만 MinIO 자체는 제외된다.
  6. MinIO가 날아가는 상황까지 대비하려면 AWS S3 같은 외부 저장소 복제가 필요하다.
  7. 백업은 만든 것으로 끝이 아니라, 복구 테스트까지 해야 의미가 있다.
최종 정리

우리 백업 구조는 하나의 도구로 모든 것을 해결하는 방식이 아니다. Kubernetes 리소스는 Velero, DB는 pg_dump, 파일은 tar, 서버 볼륨은 restic, 클러스터 상태는 etcd snapshot으로 나눠서 백업한다. 그래서 데이터 성격별로 더 안전하고 복구하기 쉬운 구조다.
