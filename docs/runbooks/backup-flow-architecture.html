전체 백업 Flow Architecture

Acer 프로젝트는 백업 대상을 Kubernetes 리소스, 클러스터 제어면, DB 데이터, 파일 볼륨으로 나누고 각 도구가 만든 결과물을 mgmt MinIO에 모은 뒤 AWS S3로 외부 복제합니다.

Kubernetes 리소스 etcd 제어면 상태 DB/설정 백업 파일 볼륨 snapshot 외부 저장소

1. 한눈에 보는 백업 흐름

각 AIO 클러스터는 자기 클러스터의 Kubernetes 백업을 직접 수행합니다. mgmt 서버는 자체 DB/파일 백업을 수행하고, 모든 백업 결과를 MinIO bucket에 중앙 보관합니다.

2. 백업 종류별 상세 Flow

발표에서는 아래 4개 흐름만 잡으면 전체 백업 구조를 설명할 수 있습니다.

1
Kubernetes namespace 백업 각 클러스터의 Velero가 매일 16:00 KST에 web-service, tailscale namespace를 백업하고 MinIO velero/<team> prefix에 저장합니다.
2
etcd snapshot 백업 각 클러스터의 CronJob이 매일 15:40 KST에 control-plane 노드에서 snapshot.db를 만들고 MinIO etcd/<team>/daily/<timestamp>에 업로드합니다.
3
mgmt DB / 설정 백업 mgmt systemd timer가 매일 15:30 KST에 PostgreSQL dump, Supabase Storage, mgmt 설정, k3d datastore를 만들고 MinIO db-backup bucket에 저장합니다.
4
mgmt 파일 볼륨 백업 restic 컨테이너가 /home/mgmt-data를 주기적으로 snapshot으로 백업합니다. Harbor, GitLab, Grafana 같은 파일 기반 서비스 데이터가 여기에 포함됩니다.
5
AWS S3 외부 복제 매일 16:30 KST에 MinIO bucket을 AWS S3로 mirror하여 mgmt 서버 또는 MinIO 장애까지 대비합니다.

3. MinIO bucket 구조

백업 결과는 하나의 bucket에 섞어두지 않고 목적별 bucket으로 나눴습니다.

velero

Kubernetes namespace 백업. velero/ljw, velero/ggg처럼 팀별 prefix를 사용합니다.

etcd

각 클러스터 control-plane snapshot. etcd/ljw/daily/<timestamp> 형태입니다.

db-backup

PostgreSQL dump, Supabase Storage, mgmt 설정, k3d datastore 백업을 저장합니다.

restic

restic repository입니다. mgmt 파일 볼륨 snapshot이 암호화되어 저장됩니다.

핵심 요약: 각 클러스터는 자기 백업을 직접 만들고, mgmt MinIO는 백업 결과를 모으는 중앙 저장소 역할을 합니다.
